# Perf gate (`tools/perf/`)

## 1. Purpose

`tools/perf/gate.sh` measures the main-thread, Core Animation and WindowServer cost of the real app
(scenarios G1-G7, G9, G10 and GP:<page>) and compares it with absolute limits and, optionally, with a pre-block build. It
exists because per-frame animation work cannot be seen by the offscreen harness or the visual baseline
(rule `gpu-per-frame`). It runs nightly (`night.sh`) and at release prep; per block only when the queue row says perf: yes.

## 2. Usage

```
tools/perf/gate.sh [--app PATH] [--baseline PATH] [--scenarios LIST] [--runs N] [--out DIR]
                   [--keep-traces] [--g1-max PCT] [--g9-max PCT]
tools/perf/gate.sh -h
```

Typical run, with Low Power Mode off (on AC or on battery; the report shows which), about 8 minutes per scenario (3 runs x 2 arms x ~75 s), **do not use the Mac while it runs**
(it moves the real pointer and sends AX actions):

```
cd MacDashboard && ./build_app.sh && tools/perf/gate.sh --baseline tools/perf/out/baseline.noindex/MacDashboard.app
```

- `--app` default `dist.noindex/MacDashboard.app`. `--baseline`: candidate and baseline runs alternate A,B,A,B so drift hits both.
- Baseline rule: the `--baseline` bundle must be built from the PERF-GATE-RETARGET merge or later, the first build with the `report-show-in-finder` identifier (G5 route). An older baseline can lack an element a route needs; that run is an ERROR on the baseline arm (tag `<item>-base<N>`, the report adds a baseline hint) and the scenario gets no verdict: rebuild the baseline from a newer commit. The night runner's baseline (its previous build) meets the rule.
- `--scenarios`: `G1..G7`, `G9`, `G10` (live-resize sweep, RESIZE-MOTION), `GP:<page>` (scroll scenario on one page: cpu memory storage battery security backups system history) or `all` (every G item plus GP for all pages); default `G1,G2,G3,G4,G5,G6,G7,G9` (G10 is not in the default list; `all` includes it). `--runs` 1-7, default 3 for every item; arms are aggregated by median.
- Both bundles are copied with `tools/bench-app.sh` (`MacDashboardBench.app`, bundle id `com.rdskcm.mac-dashboard.bench`) into `$OUT/apps`, removed at exit, and their LaunchServices records dropped by `tools/ls-prune.sh`; the app runs with `-appLanguage en -ApplePersistenceIgnoreState YES`.
- `--out` must be inside `tools/perf/out/` (gitignored); default `tools/perf/out/<stamp>`. A reused `--out` keeps the previous `summary`/`report`/`runs` files under a time-stamped name. gate.sh keeps the 5 newest `tools/perf/out/<stamp>` runs (`tools/keep-latest.sh`, log `prune.log` in the new run); named `--out` runs are never pruned.
- `--keep-traces` keeps the `.trace` bundles and exported XML (10-60 MB each). `*-analysis.txt` is always kept.
- `--g1-max` / `--g9-max` are the absolute G1 (Home idle) and G9 (CPU page idle) app CPU limits; by default gate.sh reads them from `tools/perf/budgets.tsv` (`home` and `cpu`, metric `idle_app_pct`); give them only to override for one run.

Outputs in the run directory: `summary.tsv` (`scenario arm run metric value threshold verdict`),
`report.md` (one table per scenario, power log, ERROR scenarios, defaults verdict), `power.log`, `*-analysis.txt`,
`errors.tsv` (`scenario tag reason diagnostics`, one line per ERROR run; diagnostics is `<tag>-axdiag/` for an AX miss —
AX identifier dump with frames, `drv winfo`, screenshot, display state — or the run's log for a trace or analysis failure:
`<tag>-rec.txt`, `<tag>-export.err`, `<tag>-analysis.txt` or `<tag>-drv.txt`) and `error-runs.tsv` (runs of ERROR scenarios, no verdict),
and the last stdout line `GATE: exit=<n> pass=<k> fail=<m> noisy=<j> invalid=<0|1> error=<e>`.
`analyze.py tp` refuses a trace with no samples in its window, none on the main thread, no hitches export, or (G6, with substrings) no symbolicated frame; `ca` refuses an empty commit table or a window outside the trace; `top` refuses a window with no app sample (exit 2 in every case, so the run is an ERROR). `analyze.py verdict` writes a FAIL row (value `-`, threshold `… missing for the candidate`) for a metric with an absolute limit, or with a regression rule and a baseline value, that the candidate never produced.

## 3. Exit codes

`0` pass (NOISY rows do not fail) · `1` any FAIL (absolute or regression rule) · `3` INVALID run: the power check after a run (or a `Using AC` / `Using Batt`
entry in `pmset -g log` that differs from the source the gate started on, during it) failed twice; the numbers are discarded, never averaged · `4` the defaults domain
`com.rdskcm.mac-dashboard` differs before/after (the gate runs bench copies and never writes that domain, so 4 means another process changed it; the diff is printed) · `5` ERROR: at least one scenario was not measured, because an AX element (press, frame, wait or scroll probe) was still missing after one retry, or one run's trace or analysis failed (no trace, export failed, analyze.py failed, scenario marks missing), or a scroll window left its range (§4, Scroll method); the other scenarios ran and are reported · `64` usage ·
`65` precondition refused · `70` runtime error before or around a run (cannot create the run directory, bench copy or helper build failed, the fixture could not be built, the app exited at launch, the window could not be pinned, the final verdict step failed), or a shell error: an exit 1 that does not come from the final verdict (bash exits 1 on a set -u abort) is reported as 70, so 1 always means a measured FAIL.
When several apply: 3 over 4 over 5 over 1. An AX miss is retried once after the app is brought to the front (for a
Home tile after a fresh `main-mode-mac` press); this retry is robustness. The 2026-10-20 and 2026-10-30 misses (6 or 7 of 8 Home
tiles, presses with no effect) came from a second MacDashboard process: System Events, asked for the gate's pid, returned the other process's window contents (GATE-AX-MISS). The gate now uses native AX by pid (`ax`) and refuses to start beside another MacDashboard process. After pinning, the AX window frame must equal the pid's on-screen CG window frame, else that run is ERROR (`pin: the AX window of pid … is not its on-screen window`). A second miss writes `<tag>-axdiag/`, stops that app, marks the scenario ERROR
and the gate continues with the next scenario. A trace or analysis failure is not retried: the run is ERROR at once, with the log named in errors.tsv. There is never a coordinate fallback.

Preconditions (65): Low Power Mode 0 (battery is allowed and shown in the report: "Power: measured on battery. Compare only with runs on battery."; a run of 15 minutes or more on battery prints a warning to connect the power adapter) · screen unlocked · main display at least 1280x800 pt · Accessibility
enabled (`ax 0 trusted`) · `xcrun xctrace version` works · no other `gate.sh` running · no MacDashboard process the gate did not start (installed app, dev build, another session's bench copy; listed with pid, parent, start time and command by `tools/perf/foreign-copies.sh list` — quit them first; the gate never closes them, `night.sh` does; `GATE_TEST_ALLOW_FOREIGN=1` runs beside them, for the GATE-AX-MISS verification only) · bench home not inside `~/Library`.

Limits: G1 app % <= `--g1-max`; G9 app % <= `--g9-max`; G3 median <= 25 ms/s; G4 hitches/s <= 3, median <= 400 ms/s; G5 `capsule` commits/s median <= 60 and

the candidate median must not exceed the baseline median by more than the margin (hitches + 3 for G3 G4 G6 G7 GP; main busy total x 1.15 for
G4 G6 G7 GP; app % + 0.5 for G1 G3 G9). A row over its margin is FAIL only when the exact one-sided Mann-Whitney test gives p <= 0.05
(with 3 v 3 runs: every candidate run above every baseline run); otherwise it is NOISY and does not block. A NOISY row is re-run with `--runs 5`.
G10 has no absolute limit; regression rule only, on main busy total x 1.15 (hitches are reported, not gated: a build that is already saturated during a live resize hides the animation cost in them). With `--runs` 1 or 2 a regression is always NOISY; absolute limits still apply. WindowServer numbers are reported, never gated (+-2 pt noise). Scroll scenarios (G3, G7, GP) record `scrollable` per run (1 = the scroll area under the pointer has a vertical scroll bar, 0 = nothing to scroll); when the two arms differ in it, or an arm is mixed, the regression rule is skipped for that scenario ("no regression check") and only absolute limits apply.

### Scroll method

Rule `scroll-bench-in-range`: a scroll frame measurement first reads the page's real scroll range and stays inside it, with the position logged during the window. A control window has the same range as the page it is compared with. Fixed scroll distances are not valid.

- **Range.** Before the trace attaches, `drv probe <pid> 500 450 [inner]` reads the range of the scroll area under the point: range = position change / scroll-bar change across one short leg, both read at rest. It also measures points per event (`ppe`) and the coast after the gesture ends, per build and arm, from two legs of different length (the coast cancels). The range is never computed from the extent of child element frames (short by 84-97 pt). The table's range (G6-table) is the known travel (60 events x `ppe` + coast) divided by the table bar's change. The probe's legs run with no trace attached; it leaves the page at the lower turn point.
- **Wave.** `drv wave` posts wheel events at `dy` 6 (about 294 pt/s on the built-in display) at about 49 events/s (the existing 1/60 s sleep loop), on every page. The direction flips between two turn points at measured coast + 15 pt from each end, without an `ended` event at a turn; each segment ends with one `ended`. The event count is the same on every page (G7 4 x 120, G6 page 2 x 180, G6 table 168 + 180 + 180, G6 hover 168), so motion time does not depend on page height. A page qualifies when the span between the turn points is at least 60 pt (about 152 pt of range on the built-in display).
- **Log.** During the events (not in the gaps) one attribute, the scroll-bar value, is read from one cached element at 10 Hz and written to `<run>-pos.log` (`S`/`E` mark each segment, `P` each read). All element lookup happens before `t0`. The log verifies the result; it does not steer the gesture. `analyze.py pos` gives `end_contact_pct` (reads within 3 pt of an end), `pos_reads` and `motion_s`. Logging cost (SCROLL-BENCH-EDGES V3, one build as both arms, candidate at 40 Hz and baseline at 10 Hz, GP:system, 2 runs, on battery): `read_cost` 0.2528 busy samples per read, `logging_share` 0.91 % of `main_busy_total` (limit 2 %), medians 2615.5 and 2672, reads 94 and 317.5.
- **Invalid window.** More than 5 % of the position reads within 3 pt of an end, or fewer than 50 % of the expected reads, gives no figure for the scenario: the run is ERROR with the reason (`scroll window left the page's range`) and the gate exits 5. There is no automatic re-record, since the gesture is deterministic. Night counts it as not fully measured, so the next night repeats it. One read at an end stays visible in `end_contact_pct` without failing the run.
- **Idle and too-short pages.** No vertical bar under (500,450): idle page, today's events, `scrollable 0`, no `range_pt` (G6-*: ERROR). A bar with a range too short for the gesture: `scrollable 0`, `range_pt` shown, no events (G6-*: ERROR). Arms whose ranges differ by more than 10 % keep their regression verdict; the report heading says "RANGE DIFFERS" (speed and motion time are equal, so the comparison stays fair).
- **Verification overrides.** `GATE_TEST_RANGE_SCALE` multiplies the range given to `drv wave` (forces a window out of its range), `GATE_TEST_CAND_POS_HZ` sets the candidate arm's logging rate. They are for verification only; `night.sh` unsets them.

Correction: Scroll figures from before SCROLL-BENCH-EDGES (2026-11-04) do not count as the cost of scrolling a page: those windows spent 19-92 % of their time at a page end. Which past figures stop counting and which stay valid is listed in `inputs/SCROLL-BENCH-EDGES-rig/FINDINGS-2026-11-04.md`, Q5, in the planning project.

## 5. Permissions (as `tools/visual/README.md` §3)

The terminal app that runs the gate needs Screen Recording and Accessibility (the gate's AX helper `ax` runs as its child). `night.sh` also needs Automation → MacDashboard, for the polite quit of the installed app before the gate and each job.

## 6. Data safety

- Synthetic data only: `mkfixture.py` builds `$OUT/home` from scratch for every run (500 state rows, 3 iPhones, device 0 with 1026 rows). It refuses a target inside `~/Library`, one that contains the real home, and a non-empty directory it did not create.
- The app is a bench copy (bundle id `com.rdskcm.mac-dashboard.bench`, own defaults domain, saved state deleted at launch) and runs with `CFFIXED_USER_HOME=$OUT/home`. The gate never reads, writes, copies or lists `~/Library/Application Support/MacDashboard`.
- It kills only PIDs it started and recorded in `$OUT/pids`, only while they are still its own children. No `pkill`/`killall`, no kill by name.
- It never closes another MacDashboard process; it refuses to start instead (exit 65). `night.sh` closes them (§8).
- It never installs and never touches `~/Applications/MacDashboard.app`. At exit it calls `tools/ls-prune.sh`.
- The defaults domain is exported before and after and compared; a change is exit 4, never restored.
- AX presses happen only before `xctrace` attaches; one scroll-bar value read at 10 Hz also runs during scroll windows (read-only). Helpers `drv`/`hold`/`ax` are compiled fresh into `$OUT/.bin/`; `ax` (`ax.swift`) addresses the app only by pid (`AXUIElementCreateApplication`), never through System Events.

## 7. Known limits

- Time Profiler symbol names (`rgba64_shade_conic`) change with SDKs; re-check them after a macOS/Xcode update.
- `top` timestamps have 1 s samples, so G5 windows hold 3-4 samples each.
- The G3 window is [t0, t0+7) s, i.e. 2-9 s after the scroll ends (R5). A different reading, [t0+2, t0+9), is 4-11 s after it.
- Hitch numbers include whatever the Mac does in the background; a run with the Mac in use is not comparable.
- The table's range is an estimate of the lazy content (`LazyVStack`), good enough because the wave travels a few thousand points in a far larger range and contact is judged from the bar. The post rate is about 49 events/s on every display (timer-driven, not following the refresh rate). `scrollable` relies on macOS listing a vertical scroll bar in the AX tree only when the content overflows (true on all nine pages on 2026-10-23, c557d89).
- Security and Backups content comes from the host Mac's real state (updates, crash reports, Time Machine), so GP-security and GP-backups can switch between idle page and scroll from night to night.

## 8. Night runner

`night.sh` is the one launcher for unattended night work: on an idle Mac it runs the gate on `origin/main` when main changed, then the queued night jobs until 09:00 (or a one-night stop, see D30), and writes one report for the whole night to `tools/perf/out/night.noindex/latest.md` (copies in `reports/<YYYYMMDD>.md`; a second run on the same date writes `reports/<YYYYMMDD>-2.md`, then `-3` …, never overwriting; `latest.md` is the newest; first line `NIGHT <date>: <gate verdict | SKIPPED | INTERRUPTED | ERROR …>; jobs: …`).

- Preconditions: AC power and Low Power Mode off (AC because the charge may run out during the night), screen unlocked, user idle, Claude Code not working (D28), no other gate or night run. A closed lid means no run (the first check after waking writes a SKIPPED report).
- D22: a LaunchAgent runs `night.sh --check` every 60 s; between 00:00 and 03:00 it starts one run per night by opening `night.command` in Terminal, so the run inherits Terminal's Accessibility, Screen Recording and Automation grants (keep them).
- D23: idle threshold 10 min, or the display-sleep time minus 2 min when that is shorter (minimum 60 s).
- D24: `caffeinate -d -i -s` holds the Mac and display awake for the whole run; the report records the assertion.
- D25: the display (DisplayServices or IOKit) and the keyboard backlight (CoreBrightness `KeyboardBrightnessClient`, private framework) are dimmed to 0 for the run (`brightness.swift`) and restored at the end, on Ctrl-C and by the next `--check` after a crash; where one cannot be set the run continues and the report says "not settable". A start value below 0.05 (system idle dim, keyboard auto-off) is not saved and not dimmed, so it is never "restored" as black.
- D26: the candidate is `origin/main` (fetch with BatchMode; offline uses the local ref); the baseline is the previous night's build; the same SHA as the last full measurement is SKIPPED "main unchanged".
- D27: with no earlier finished build there is no baseline, so only absolute limits apply. `builds/` is pruned to the candidate and the baseline only after a successful full measured run (gate exit 0, or 1 with a measured FAIL); after any other exit (also 5, ERROR) or a partial run nothing is deleted, and exit 5 does not mark the SHA as measured, so the next night measures it again.
- D28: `--check` does not start while Claude Code is working: a transcript (`*.jsonl` at any depth under `~/.claude/projects`, main sessions and subagents) modified in the last 15 min whose newest line of type `user`, `assistant`, `attachment` or `api-request` has a `timestamp` inside those 15 min. Service lines (`artifact-autoreact-ledger`, `system` notes, `queue-operation`, `file-history-snapshot` and other bookkeeping types) and lines without a timestamp do not count (NIGHT-QUIET-CHECK: an idle session's ledger lines blocked the 2026-11-08 jobs). HID idle alone let a run start while agents worked with the user away (2026-10-26), which is why this check exists. If the check itself fails it counts as working. It is the first start condition checked; the skip reason (count, time of the newest work line, path) goes to `agent.log` and, on a night that never starts, into the SKIPPED report.
- D29 (NIGHT-START-LOCK): from 21:00 until the night's run starts, at 03:00 at the latest, `--check` keeps one `caffeinate -d -i -s -t <until 03:00>` alive in its own process group, so the console cannot lock while the run waits for its start conditions (2026-10-31 was skipped: locked at 02:06, Claude Code quiet at 02:07). Not on battery or Low Power Mode, not while the screen is locked; never two. While the user is idle for the idle threshold the display and keyboard are dimmed to 0 through the run's saved-value files (`state/hold-dimmed` marks that the hold owns them); input restores them within one tick. The run ends the hold after its own assertion is verified and keeps the lights dark. Events: `hold: …` in `agent.log`, `evening hold: …` in the report.
- D30 (NIGHT-QUIET-CHECK): `night.sh --stop-tonight HH:MM` (after 03:00, before 13:00) sets the job stop of the coming night's automatic run: tonight's before 03:00, otherwise the next one. It is stored in `state/stop-tonight` with its night and ignored on every other night, which stop at 09:00 again; `--stop-tonight 09:00` undoes it. Hand runs keep `--stop`. Refused once that night's run has started. `--queue-list`, `--check --dry-run`, the `--queue-add` message and the report's `time:` line show it.
- The morning report lists the scenarios that had nothing to scroll (`idle page, nothing to scroll …`).
- Install and remove: `tools/perf/night.sh --install` / `--uninstall`. After a restart or crash, `--restore-brightness` puts back a saved value.
- Hand run: `tools/perf/night.sh --run --now` starts a "Mac idle" run at once (skips window and idle checks) and runs the gate only (~2.6 h full); the queue is untouched. `--now --stop HH:MM` also runs the queued jobs until that time; `--now --stop HH:MM --no-gate` runs jobs only. `--scenarios G1 --runs 1` takes ~5 min plus the build and is a check of the runner; a run with other scenarios than `all` is marked "partial". `--keep-dark` leaves display and keyboard dark after the run (the user restores them by hand).
- `--check --dry-run` prints the decision and starts nothing. With `NIGHT_HOUR=<0-23>` it decides as at that hour, with `NIGHT_CLAUDE_PROJECTS=<dir>` it looks for transcripts in that folder; with `NIGHT_DATE=<YYYYMMDD>` it decides as for that night (no started marker, its own skip and report files); `NIGHT_DATE` is ignored without `--dry-run`, `NIGHT_HOUR` is also honoured with `NIGHT_OUT` (then 3-23 only, so a test tick never opens a real run); `NIGHT_IDLE=<s>` (with `--dry-run` or `NIGHT_OUT`) is the HID idle the evening hold sees, never the start check. `NIGHT_OUT=<absolute dir>` replaces `tools/perf/out/night.noindex` (state, queue, builds, reports) in every mode except `--install`/`--uninstall` and also enables `NIGHT_CLAUDE_PROJECTS`: a day-time test state that never touches the real queue or reports. `--dry-run` creates, writes and logs nothing. `NIGHT_FOREIGN_ONLY` is honoured only with `NIGHT_OUT`.
- **Jobs**: `night.sh --queue-add --name NAME --minutes M --dir DIR --cmd 'COMMAND'` queues a job in `out/night.noindex/queue/` (survives sessions; bad input exits 64); `--queue-list` shows the queue in run order; `--queue-remove ID` removes a waiting job. `minutes` is the time the job needs before the night's stop (09:00, or the D30 one-night stop) to be worth starting (the full length of a fixed-length job, the minimum useful time of a job that stops itself at `STOP_AT`). Jobs run in queue order, one at a time, after the gate; a job whose minutes do not fit before the stop is not started, stays queued, and the next one is tried. The job runs in the foreground (`/bin/bash -c`, in DIR, stdin `/dev/null`) in its own process group with `STOP_AT` (stop minus 15 min), `NIGHT_STOP_EPOCH`, `NIGHT_JOB_DATE` and `NIGHT_JOB_ID` in its environment; at the stop the group gets SIGTERM and SIGKILL 120 s later. A started job leaves the queue with DONE / FAILED exit N / STOPPED AT <stop> / INTERRUPTED and the report prints its re-queue command; there is no automatic retry. A job must not detach (`nohup`, `&`): what it leaves behind after its exit is killed.
- **Standing set** (NIGHT-STANDING-JOBS): `night.sh --standing-add --name NAME --minutes M --dir DIR --cmd 'COMMAND'` adds a job to `out/night.noindex/standing/` (same checks as `--queue-add`, a duplicate name exits 64); `--standing-list`, `--standing-remove NAME`. Every automatic night run starts the standing jobs after the queued jobs, in the order added, with the same start checks; M is both the time a job needs before the stop and its cap (`NIGHT_STOP_EPOCH` = start + M, `STOP_AT` 15 min earlier, SIGTERM at the cap). A standing job is skipped on a night when a queued job of the same name was started in that run. Hand runs run the set only with `--now --stop HH:MM --standing`. The job file stays; the rig must end its output with a line `out: <dir>`.
- **Morning diff**: for a DONE standing job, `tools/perf/standing-diff.py` compares its `out:` directory with the previous DONE run (`standing/last-<NAME>`) and the report's `## standing` section shows the result (SAME / CHANGED / FIRST / NORULE and up to 15 lines); line 1 ends with the standing counts including "<n> changed". Rules: MAIN-THREAD-AUDIT manifest rows move by ≥ x1.25 and ≥ 1 % of one core (cpu_ms) or ≥ 1000 SwiftUI rows, or nav/toc change; MEMORY-LEAK-CHECK trend words or leak-stack counts change. A new standing job adds its rule there.
- **Budgets** (PAGE-BUDGETS): `tools/perf/budgets.tsv` holds the allowed cost of every page and is the only copy of those numbers (`*` = every page without its own row); its comments give each value's derivation and sources. Metrics: `idle_app_pct` (app CPU, % of one core, page shown, nobody at the Mac; gate G1/G9 reading when the newest `night-*` gate run measured this build, else the MAIN-THREAD-AUDIT Time Profiler row, which includes Time Profiler's own overhead) and `hitch_ms_per_s` (hitch time ratio, 5 ms/s at most, Apple's good threshold, WWDC20 10077; a frame later than its 6.94 ms deadline at 144 Hz is a hitch; no night job measures it yet). `budgets.py read` writes the report's `## budgets` section and the `budgets: <o> over, <w> within, <n> no data` part of line 1; lines are over, within, then grouped no data, and `traced minus gate` shows the instrument overhead. `budgets.py get PAGE METRIC` prints one budget; `budgets.py selftest`. To change a budget, edit its row and its basis; gate.sh and the report follow.
- **Morning report**: written at the end of the run (gate block, one block per job with its last 3 output lines, the standing block, the budgets block, the jobs still waiting). For a night without a finished run, the first `--check` after 03:00 writes it (SKIPPED or INTERRUPTED) at any hour, also for yesterday's night; never while a run or gate is alive.
- **Other MacDashboard processes** (GATE-AX-MISS): before the gate and before each job `night.sh` runs `foreign-copies.sh close`. Every copy that is not the installed app (bench copies, `dist.noindex` builds, scratchpad copies) gets SIGTERM, then SIGKILL after 5 s. The installed app (`/Applications` or `~/Applications`, bundle id `com.rdskcm.mac-dashboard`) gets one AppleScript quit with a 15 s limit and is never killed, so an app left open overnight is closed in the morning. The report lists every process found (`pid ppid started command`) and how it was closed. If one is still running, the gate is SKIPPED, or the job is NOT STARTED and stays queued, with the pids in the report. This applies to a hand `--run` too. Test seam: `NIGHT_FOREIGN_ONLY=<pid>` with `NIGHT_OUT` acts on that process only.
- **Rig example**: PERF-EFFECT-BREAKDOWN as a job: `tools/perf/night.sh --queue-add --name perf-effect-night2 --minutes 120 --dir "<project>/inputs/PERF-EFFECT-BREAKDOWN-rig" --cmd "OUT=out/night2 KTRACE_CLEAN=1 REPS=3 MATRIX=<follow-up matrix> ./run.sh"`: `./run.sh` in the foreground, no `nohup`/`&`, no `DIM` (night.sh owns the lights), no `STOP_AT` (night.sh exports it), a fresh `OUT`. night.sh closes MacDashboard processes before the job, so the job needs no quit of its own.
- **Retention**: `tools/keep-latest.sh [--dry-run] PARENT REGEX KEEP` keeps the KEEP newest runs (name order) of one kind and deletes older ones unless a queued job or a standing `last-*` file names them; it refuses folders outside `tools/perf/out` and `tools/visual/out`. Kinds and counts: gate stamp runs 5, `night-<date>` gate runs 5 (night.sh), `mtaudit.noindex` full 3 / smoke 2, `leakcheck.noindex` full 5 / smoke 2, `snap-<stamp>` 5, visual smoke `<stamp>` 5. `night.noindex`, `baseline.noindex` and named runs are never pruned.
